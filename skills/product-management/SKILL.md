# Product management

## 資料權責

| Notion 資料庫 | 記錄 |
|---|---|
| `專案` | 目標、優先順序、負責人、日期、健康度與里程碑 |
| `問題追蹤` | 使用者問題、錯誤、影響及重現證據 |
| `功能要求`，`記錄類型=產品需求` | 產品結果、範圍與可觀測驗收條件 |
| `功能要求`，`記錄類型=開發任務` | 一次工程交付的規格、負責人、狀態與驗收證據 |
| `工程文件` | 已發布的 PRD、技術規格與架構決策 |

開發任務與產品需求同在 `功能要求`，以 `記錄類型` 分辨；**不另建開發任務資料庫**。
`對應需求` 是可含多筆產品需求的 relation，`開發任務` 是其反向欄位；一筆開發任務
可解決多筆需求，一筆需求也可由多筆任務完成。`來源問題`、`工程文件`、`所屬專案` 保留
問題、規格與專案的來源關係。頁面內的待辦勾選項不取代獨立開發任務。

## 開案與收斂

1. 讀回四個資料庫的 schema 和現有頁面，以來源 ID、標題與關聯查重。已有對應頁面就更新
   既有頁面，不建立第二筆。Linear 欄位與 URL 僅作遷移來源及歷史追溯，不作現行案件入口。
2. 把原始問題記在 `問題追蹤`；把產品要達成的行為、非目標與逐條驗收寫在 `產品需求` 頁。
   `工程文件` 的 `已發布` 頁面提供現行詳細規格。來源衝突時停在需求釐清，並記錄差異。
3. 對照共用的工程變更，再建立或更新 `開發任務`。在任務頁寫明所涵蓋的需求、工程範圍、
   技術方案、依賴、測試與失敗處置；填入 `對應需求`、`來源問題`、`工程文件`、`所屬專案`。
   多個需求由同一變更滿足時使用同一任務，不按來源頁數複製任務。
4. 保存後重新 fetch 任務與關聯頁。確認 `記錄類型=開發任務`、`工作項目 ID`、URL、
   負責人、開發規格與驗收條件齊全，才交給 `engineering-delivery`。頁面仍為 `新` 或
   `審核中` 的產品需求不可自行當成已核准範圍。

## 專案與驗收

專案日期與健康度引用當前證據；里程碑可放在專案頁，寫明目標日、狀態及 owning 任務。
工程、CI、部署、runtime、產品接受分層記錄。`驗收狀態=待產品接受` 表示技術驗證已有
證據；`已接受` 和 `已發表` 只由 product owner 決定。

每次需求決策、任務拆合、阻塞與驗收都寫回相應 Notion 頁面並讀回。包含憑證或私人資料的
原始 log 先遮罩，只保留 ref 和必要摘要。

## Linear 遷移

遷移時先查 `Linear ID`，建立後讀回來源 ID、URL、內容、狀態與關聯；重跑只補缺項。
保留原始 `Linear 狀態`，不得把 Done 自動寫成 `已發表`，或把 Canceled 自動寫成
`不會修正`。歷史 Linear 頁面保留為來源連結；現行決策與寫回都在 Notion。
