WHAT IT DOES 01 — 03

Consistent delivery rules
for software engineering.

When an agent starts software development, fixes a bug, reviews code, works on a pull request, or deploys, JT Harness provides consistent rules for tracking the work and verifying delivery.

01 / TRACK

Keep work traceable

Find or create the Linear issue first. Keep small tasks actionable with their approach and acceptance; link a shared spec for features spanning issues. Record the outcome, pull request, reviews, checks, and merge status when finished.

02 / ROUTE

Use the right tools

Use the Coolify Skill for Coolify resources, and the Hetzner Skill for Hetzner Cloud and Storage Box.

03 / REVIEW

Clear review gates

Use one complete current-head review each with Codex and CodeRabbit. Code, tests, scripts, operational agent instructions or policies consumed by the repository/plugin, and any configuration PR also require Pstack interrogate and no-comments. Documentation/content-only PRs confirm there are no code, operational-policy, or configuration changes, record Pstack as not applicable, and complete a content audit: verify factual claims against canonical repository or authoritative sources and validate links and command/file examples. For every content audit, record changed paths, claim/source pairs, link/example results, and the audited commit SHA. Inspect rendered output only when formatting or page layout changes. Re-audit any documentation/content paths changed after that commit before merging. Media-only PRs complete media acceptance. If Codex or CodeRabbit explicitly reports an error or rate/usage limit, or finishes without a result, record that reviewer exception without retrying or requesting a replacement; the other reviewer still needs a complete current-head review. Other failures, skipped reviews, and incomplete results remain unmet. Resolve actionable Codex and CodeRabbit findings and verify fixes before merging. Resolve or explicitly reject actionable Pstack findings before merging. After findings are fixed, obtain focused correction-delta verification from each reviewer that was not ignored; do not repeat a full review on unchanged scope. If both reviews are ignored under the stated exceptions, Pstack-required PRs still require the Pstack review, documentation/content PRs require the content audit, and media PRs require media acceptance. Local full-project lint must pass, including existing main failures. Once current-head required checks pass and GitHub reports the PR mergeable, merge directly. Delivery PRs should not be opened as drafts; if one is already a draft, mark it ready immediately. If automatic reviews do not start on a ready PR, request each required review once. Record actual GitHub blockers without bypassing platform restrictions. Do not merge review-only or explicitly no-merge work.

GET STARTED INSTALL

Choose your platform.

Install from the official repository. New versions are published on GitHub Releases.

01 / CODEX Codex

Add the JurisLM marketplace and install the plugin from your terminal:

codex plugin marketplace add https://github.com/jurislm/jt-harness-plugin --ref main
codex plugin add jt-harness-plugin@jurislm-jt-harness

After installing or updating, start a new Codex session to load the Skill.

02 / CURSOR Cursor
  1. Open Customize → Plugins.
  2. Choose From GitHub Repository.
  3. Enter https://github.com/jurislm/jt-harness-plugin and install jt-harness-plugin.

After updating, reload Cursor and confirm the using-jt-harness Skill appears.

SCOPE WHAT IT IS

A Skill, not
another service.

The JT Harness Skill is automatically invoked and provides delivery rules. When installed on the current host, prefer the official Pstack for engineering methods. Pstack interrogate and no-comments apply to code, tests, scripts, operational agent instructions/policies, and any configuration PRs; documentation/content-only and non-executable-media-only PRs confirm no such paths changed, record Pstack as not applicable, and complete the content audit or media acceptance. JT remains the delivery-policy source and does not duplicate another methods framework. The main/root checkout is read-only for task development: when clean and safe, update it with git pull --ff-only; do not edit task files, commit task changes, or directly push development changes from it.
